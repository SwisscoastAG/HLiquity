  • The race window is the vulnerability users can close. CONFIRMED (community forensic analysis of mainnet data — methodology in §2 and the appendix)

02Incident recap — what happened and what it cost

All incident facts below come from community forensic analysis of public mainnet data (methodology in this section and the appendix); this section carries only what the build decision depends on. CONFIRMED

Root cause. CWE-862 (Missing Authorization) confused deputy: the HLiquity token wrappers inherit an ungated transferFrom helper (selector 0x15dacbea) that spends any standing HTS allowance without checking who is asking. Users grant allowances to the wrapper contracts (all HTS pulls execute via precompile 0x167), which is the vulnerable surface. The attacker’s sweeper bot — gas relayer 0.0.995584, receiver 0.0.10393273 — watched for new allowance grants and spent them, typically within seconds. Reference transaction 0.0.995584-1790680920-326001014 (view on HashScan): 1,800 HCHF drained from victim 0.0.846778, 7 seconds after the victim’s approval. The victim’s subsequent protocol redeem executed and reverted atomically (HTS status 292, SPENDER_DOES_NOT_HAVE_ALLOWANCE) — the protocol behaved correctly; the loss happened in the gap between the two user transactions.

3.1  Fact-check: the March 2027 deprecation VERIFIED-NARROWED

Fact-check box — the deprecation the assessment warned about

Source: official Hedera blog, 2026-09-22 — “Atomic Batch Transactions No Longer Support Smart Contract Calls.” CONFIRMED (the blog exists and says exactly this) · INFERENCE (treating “estimated” as a hard planning date).

“Smart contract calls submitted as inner transactions of an Atomic Batch Transaction enter a six-month deprecation period, with removal planned for March 2027. Atomic batch transactions remain fully supported for composing native Hedera service operations.”Blog quote 1 — deprecation + what survives “As of September 2026: a batch may contain no more than one smart contract call, and it must be the final inner transaction.”Blog quote 2 — current constraint (matches services v0.77 behavior) “From March 2027: smart contract calls are no longer supported as inner transactions of an atomic batch.”Blog quote 3 — the removal “March 2027, estimated.”Blog, timeline — the narrowing: no committed date

Load-bearing implication. Our exact mitigation — approve + ContractCall in a batch — stops working around March 2027. No official March-2027 ban on native batches, atomic swap, or allowance behavior exists (searched; none). Stated rationale for the removal: EVM compatibility — “no equivalent construct in the EVM.” Precedent says Hedera executes such deprecations: the 2023-03-09 precompile attack (~$600K) was answered first by an emergency proxy-access shutoff and then permanently in services v0.34.5 (blocking delegatecall→precompile), followed by the HSCS Security Model v2. Plan for the sunset as real, keep the buffer, and do not let the router depend on batch inners at all.

04Why atomic batches close the race

The sweeper bot wins because the vulnerable state — a live, unspent allowance to the wrapper — exists between two user transactions, visible to anyone polling the mirror node (bot cycle ~30–60 s, response in seconds — community monitoring of mainnet data, §2). HIP-551 inner transactions execute sequentially, in listed order, inside a single consensus transaction. In a batch, the allowance transitions nonexistent → set → consumed → zero with no inter-transaction gap, and if the redeem fails, the approve rolls back with it — no residue for the bot to take later. CONFIRMED (semantics, network source) INFERENCE (race-elimination claim — strongest available, no window exists by construction; see §08 residual risks) One honest caveat, added in community-2.0: a committed redeem can consume less than approved when the redemption hints truncate the amount — approve the truncated amount and verify the residue allowance immediately after (§05 steps 4d–5).

4.1  The one-contract-op-last rule — and why our shape fits

Mainnet constraint since 2026-09-29 (services v0.77, AtomicBatchHandler.pureChecks): a batch may contain at most ONE inner transaction that is a contract operation (CONTRACT_CALL, CONTRACT_CREATE_INSTANCE, or ETHEREUMTRANSACTION), and it must be the last inner; anything else pre-checks INVALID_TRANSACTION_BODY. Forbidden inner types (network blacklist): Freeze, AtomicBatch (no nesting), ScheduleCreate, ScheduleSign. Allowed native types include CRYPTOAPPROVEALLOWANCE and CRYPTOTRANSFER. Our mitigation shape [CryptoApproveAllowance, ContractCall] satisfies the rule exactly — confirmed in practice by the community mainnet reproduction (§3.3). Two contract calls in one batch (e.g. approve-token + redeem as two EVM calls) is not possible — approve must be the native HTS allowance transaction. CONFIRMED

Step 4 — Pre-flight: association check, price, and redemption hints

redeemCollateral needs a price and three hints. Both come from read-only queries — free, and they catch the failure modes before any fee is spent. If the account is not yet associated to HCHF, add a TokenAssociateTransaction as the batch’s first inner (association is a native op, allowed in any position). CONFIRMED

const {
  ContractCallQuery, ContractFunctionParameters, AccountInfoQuery
} = require("@hashgraph/sdk");

const HCHF = require("@hashgraph/sdk").TokenId.fromString("0.0.6070123");
const PRICE_FEED = "0.0.6070082", HINT_HELPERS = "0.0.6070047";

// 4a) association check (before spending an inner tx on it)
const info = await new AccountInfoQuery()
  .setAccountId(client.operatorAccountId).execute(client);
const associated = info.tokenRelationships.get(HCHF.toString()) !== undefined;
console.log("HCHF associated:", associated);

// 4b) PriceFeed.lastGoodPrice() — public getter
const price = await new ContractCallQuery()
  .setContractId(PRICE_FEED).setGas(200_000)
  .setFunction("lastGoodPrice").execute(client);
const lastGoodPrice = price.getUint256(0);

// 4c) HintHelpers.getRedemptionHints(amount, price, maxIterations) — maxIterations is a
// deliberate cap: higher scans more troves per call at higher gas. Choose it on purpose.
const hints = await new ContractCallQuery()
  .setContractId(HINT_HELPERS).setGas(1_200_000)
  .setFunction("getRedemptionHints",
    new ContractFunctionParameters()
      .addUint256(amount)          // HCHF amount, 8-dec raw units
      .addUint256(lastGoodPrice)
      .addUint256(maxIterations))
  .execute(client);
// decode per ABI: (address firstHint, uint partialNICR, uint truncatedHCHFAmount)
const firstHint = hints.getAddress(0);
const partialNICR = hints.getUint256(1);
const truncatedAmount = hints.getUint256(2); // what the call can ACTUALLY consume

// 4d) TRUNCATION RULE — never approve more than the call will consume:
// if truncatedAmount < requested amount, EITHER abort and re-run this pre-flight
// with fresh hints / a higher maxIterations, OR set amount = truncatedAmount and
// continue. Even then, stale hints or a state change between pre-flight and
// execution can leave partial consumption — check the residue allowance
// immediately after execution (step 7).

Step 5 — Build the two inners (approve first, contract call last)

Approve the amount the call will actually consume — for redemption, the truncated amount from step 4d, never more. Zero residue is guaranteed only when the call consumes the exact approved amount: true by construction for the fixed-amount flows (provideToSP, repayHCHF, stake), not guaranteed for redemption (truncated or stale hints can leave partial consumption) — hence the mandatory residue check in step 7. batchify(client, key) sets the batch key, signs with the payer key, and freezes (forcing node account 0.0.0). addInnerTransaction throws unless the inner is frozen with a batchKey set (that is what batchify did). The outer must then be signed by every distinct batchKey key plus the payer — with one key as batchKey on all inners, that key signs everything. CONFIRMED

  • The blokk fork already qualifies. blokk-studio/HLiquity runs @hashgraph/hedera-wallet-connect ^1.4.2 + @hashgraph/sdk 2.72.0 (≥2.64 required — satisfied) and builds a native ContractExecuteTransaction per call today. The batch migration is a wrapper change, not a stack change. CONFIRMED (evaluating the 2.1.x connector line: §08 open questions)
  • What remains unverified: how HashPack renders the inner details inside each signing prompt (no public screenshots/descriptions; the mainnet test observed three prompts but did not settle the rendering question), and the single-prompt hedera_signAndExecuteTransaction path for a batch containing a contract call. 6.2  Architecture: BatchTxBuilder around the existing builders

Keep every existing ContractExecuteTransaction builder untouched. Add one BatchTxBuilder that wraps a flow: build approve inner (native, exact amount, correct spender) → take the flow’s existing contract-execute builder as the final inner → set explicit inner transactionIds (TransactionId.generate(userAccount)) → set the user’s public key as batchKey on every inner → freeze for the wallet signer (no SDK operator client exists in the frontend — the wallet is the signer). This no-operator freeze + wallet-signing pattern was assembled for the previous community edition and is now validated on mainnet via connector 1.5.1 (§3.3) — keep it behind the §6.7 regression tests on every connector bump. Batch assembly and the one-contract-op-last invariant are enforced in one place, so the 7 flows cannot drift out of compliance. Reference TypeScript (BatchTxBuilder, the 7 flow builders, the React hook, and the HashPack version gate) is published alongside this document in the repository under code/frontend/.

6.4  Signing model — validated pattern, plus the #694 version caveat

Validated on mainnet (§3.3): per-transaction signing, three prompts. The dapp builds and freezes the batch without an operator, then the wallet signs each inner transaction individually and the outer batch separately — three signing prompts — using the HIP-820 sign method of hedera-wallet-connect 1.5.1; the dapp then relays the signed bytes with hedera_executeTransaction. This validates the no-operator freeze + wallet-signing pattern of §6.2 end-to-end, with HashPack ≥14.4.0 as the signing wallet. CONFIRMED (community-validated, connector 1.5.1)
Version-dependent caveat — hedera-wallet-connect issue #694. On some connector versions, DAppSigner.signTransaction rebuilds the ContractExecute body and returns a signature over the rebuilt bytes, not the original — which breaks naive sign-then-submit for a batch containing a contract call. The validated 1.5.1 per-transaction path signs the original bytes and is not affected. Present #694 as a re-test trigger on connector bumps — not as a blanket mandate against signing-and-relaying, and not as a reason to prefer the unvalidated single-prompt path. CONFIRMED (issue open) / INFERENCE (scope by version)

Separate path, still unvalidated: single-prompt hedera_signAndExecuteTransaction (wallet signs and submits in one prompt) for a batch containing a contract call. No community test has validated it; keep it behind a testnet gate until scenario T3/T2-style evidence exists. Wire format for both paths: base64 transactionList + signerAccountId. After relay/submission, poll the mirror node for the batch id and inner statuses (parent ATOMICBATCH, inners linked by parent_consensus_timestamp/nonce) and only then resolve the UI promise — the wallet’s return is the submission, not finality. UNVERIFIED (single-prompt path) / CONFIRMED (wire format; mirror-node model)

6.5  UX requirements

  • Anticipate three signing prompts — and explain them before the wallet opens. The validated wallet flow (§6.4) presents one prompt per inner transaction plus one for the outer batch (inner 1, inner 2, outer). A user expecting a single prompt will suspect a bug or an attack: the UI must say three prompts are coming and show a plain-language line for each inner (approve X HCHF to wrapper 0.0.6070122; redeem X HCHF for collateral). What HashPack renders inside each prompt is UNVERIFIED — until scenario T2 lands, treat wallet rendering as unknown and make the dapp-side preview authoritative.
  • Exact-amount display, always. Show the precise approve amount in HCHF/HLQT/LP units; never “unlimited”, never rounded. For closeTrove the approve amount is net debt (debt − 20 HCHF), not the displayed full debt (§2.1). Exact amounts make residue zero by construction for the fixed-amount flows (provideToSP, repayHCHF, stake) — redemption is not fixed-amount: hints can truncate the consumed amount (§05 step 4d), so approve the truncated amount and check the allowance immediately after; zero residue is not absolutely guaranteed for large redemptions on the immutable contracts.
  • Residue allowance check + auto-zero. Post-execution, query /accounts/{user}/allowances/tokens; residue must be 0. If any residue is found (truncated redemption, non-atomic fallback, partial failure), surface a one-click revoke and block further batched operations until cleared. For redemption this check is mandatory, not optional — it is the only way to catch truncation residue.
  • HashPack version gate. Detect < 14.4.0 before connecting and show an upgrade path; do not silently degrade.
  • Graceful fallback = warn-and-proceed non-atomic. For wallets without batch support: explicit warning that the 7-second exposed window returns, a recommendation to use the §05 CLI instead, and — if the user proceeds — a mandatory post-tx revoke prompt. Fallback must never be silent.
  • Honest fee estimate. Show max fee covering the batch fee + each inner’s full fee, and state that inner fees are charged even if the batch rolls back (§4.2).

6.6  Security checklist

  • Exact-amount approvals only; no unlimited approvals anywhere in the fork (including legacy non-batched paths).
  • closeTrove approvals are exactly net debt (debt − 20 HCHF), never the full debt — approving the full debt leaves a standing 20 HCHF allowance to the wrapper, sweepable by the same mechanism this guide closes (§2.1). Unit-test the builder on this: approve amount must equal displayed debt minus 20 HCHF (GasPool compensation).
  • batchKey is the user’s own public key from the wallet session; the frontend never sees, holds, or transmits a private key.
  • All contract/token ids from the 2026-10-05 fingerprinted set (§05 step 3) — never from repo configs; ship a verified address manifest with the frontend.
  • Canonical HLQT HTS 0.0.6070128 only — counterfeit-HLQT confusion is an active risk (§08); verify wrapper 0.0.6070127 is the spender before building.
  • Enforce the invariant in code: exactly one contract op, last position; unit-test the builder against INVALID_TRANSACTION_BODY shapes.
  • Redemption path decodes and uses the third getRedemptionHints return (truncatedHCHFAmount): approve and call with the truncated amount, or abort — never approve more than the call consumes (§05 step 4d).
  • Log batch id + inner ids for every operation (audit + incident replay); mirror-node residue check runs before showing success.
  • Pinned dependency versions; WalletConnect project id locked to the deployer’s; supply-chain review when bumping the connector to 2.1.x.
  • Testnet sign-off before any mainnet enablement; mainnet pilot with small amounts first (§07).

9.4  Changelog

community-2.0 (2026-10-05). Mainnet validation by a community contributor; corrections to closeTrove approval amount, maxFeePercentage decimals, redemption truncation, router scope, and signing patterns. One line per correction:

  • Mainnet validation — PROVEN (§3.3): a community contributor reproduced the batched redemption on mainnet — [CryptoApproveAllowance 1 HCHF] + [TroveManager.redeemCollateral] as the final inner under one parent AtomicBatch; the batch succeeded, exactly 100,000,000 units were consumed and burned, HBAR was returned, and the residue allowance was zero; the mirror record confirms ordering and shared parent. Evidence in the GitHub issue; the contributor remains unnamed unless they request attribution. Three signing prompts observed (inner 1, inner 2, outer batch).
  • closeTrove approval amount (safety-critical, §2.1/§05/§6.3/§6.6): approve exactly net debt (debt − 20 HCHF); the GasPool provides the 20 HCHF gas compensation. Approving the full debt leaves a 20 HCHF stealable allowance.
  • maxFeePercentage decimals (§05): corrected to the deployment’s 8-decimal fixed point (BaseMath DECIMAL_PRECISION = 1e8): 100% = 1e8, 0.5% floor = 500_000.
  • Redemption truncation (§05 steps 4d–5, §6.5): decode and use the third getRedemptionHints return (truncatedHCHFAmount) — approve and call with the truncated amount, or abort; never approve more than the call consumes. Stale hints or state changes can still cause partial consumption: check the allowance immediately after. No absolute zero-residue guarantee for large redemptions on the immutable contracts; the zero-residue-by-construction phrasing now applies to fixed-amount flows only (provideToSP, repayHCHF, stake).
  • Router scope narrowed (§3.2/§07/§08): durable router = permissionless redemption ONLY — closeTrove/adjustTrove act on msg.sender and cannot be routed for existing users; SP exits, unstaking, and claims need no router (standalone calls keep working after March 2027); existing-user trove operations = batches until cutoff / migration / v2.
  • Signing patterns (§6.4/§6.5/§6.7): per-transaction signing (three HashPack prompts via hedera-wallet-connect 1.5.1, relay via hedera_executeTransaction) validated on mainnet; the single-prompt hedera_signAndExecuteTransaction path remains unvalidated; issue #694 reframed as a version-dependent caveat, not a mandate.
  • Test defaults labeled (§05): fixed gas values and the zero-hints fallback are test defaults — calibrate on testnet, use live hints from HintHelpers, and cap maxIterations deliberately.
