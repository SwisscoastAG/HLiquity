HLiquity Emergency Exit: Atomic Batch-Transaction Implementation Guide — Community Edition

How anyone maintaining or mirroring a HLiquity frontend can close the allowance-sweep race window for every user exit flow, without touching the immutable mainnet contracts: HIP-551 atomic batch transactions now, a permissionless redemption router in parallel, and a disciplined wind-down ahead of Hedera’s March 2027 removal of smart-contract calls from atomic batches. Includes a complete no-frontend CLI walkthrough and the frontend build, signing-model, UX, security, and test-plan specification. Everything in this document is a proposal that community contributors can adopt, adapt, or take over — nobody mandates anything. Mainnet-validated (community-2.3): a community contributor reproduced the batched redemption on mainnet — see §3.3 — and the CLI now uses the same JSON-RPC simulation path after Hedera rejected an SDK local query for fetchPrice().

01TL;DR — executive summary

  • The race window is the vulnerability users can close. The 2026-09-29 drain executed ~7 seconds after the victim’s approval: between the approve transaction and the redeem transaction, the HCHF allowance stood live on-chain and the sweeper bot spent it. CONFIRMED (community forensic analysis of mainnet data — methodology in §2 and the appendix)
  • No on-chain fix exists. The HLiquity core contracts are immutable and ownership-renounced — verified on-chain. Every mitigation is off-chain; this document is the engineering guide for that mitigation. CONFIRMED
  • The mechanism: HIP-551 atomic batches. Put [CryptoApproveAllowance → ContractCall] into one batch: either every inner transaction commits or all roll back. Mainnet has supported Atomic Batch Transactions since 2025-10-09 (services v0.66). CONFIRMED
  • Our shape fits the network rule exactly: since 2026-09-29 (services v0.77) a batch may contain at most ONE contract operation, and it must be the last inner transaction. Approve-first + redeem-last complies; two contract calls in one batch is not possible. CONFIRMED

Three signing prompts observed. The assembled wallet flow is upgraded from UNVERIFIED to CONFIRMED (community-validated). CONFIRMED
  • Batching removes the inter-transaction gap in which the bot operates: allowance is set and consumed inside a single consensus transaction, with zero residue if the batch rolls back. This is the only change that closes the 7-second window without touching a contract. RECOMMENDATION INFERENCE (mechanism CONFIRMED; residual-risk claim §04/§08)

02Incident recap — what happened and what it cost

All incident facts below come from community forensic analysis of public mainnet data (methodology in this section and the appendix); this section carries only what the build decision depends on. CONFIRMED

Root cause. CWE-862 (Missing Authorization) confused deputy: the HLiquity token wrappers inherit an ungated transferFrom helper (selector 0x15dacbea) that spends any standing HTS allowance without checking who is asking. Users grant allowances to the wrapper contracts (all HTS pulls execute via precompile 0x167), which is the vulnerable surface. The attacker’s sweeper bot — gas relayer 0.0.995584, receiver 0.0.10393273 — watched for new allowance grants and spent them, typically within seconds. Reference transaction 0.0.995584-1790680920-326001014 (view on HashScan): 1,800 HCHF drained from victim 0.0.846778, 7 seconds after the victim’s approval. The victim’s subsequent protocol redeem executed and reverted atomically (HTS status 292, SPENDER_DOES_NOT_HAVE_ALLOWANCE) — the protocol behaved correctly; the loss happened in the gap between the two user transactions.

3.1  Fact-check: the March 2027 deprecation VERIFIED-NARROWED

Fact-check box — the deprecation the assessment warned about

Source: official Hedera blog, 2026-09-22 — “Atomic Batch Transactions No Longer Support Smart Contract Calls.” CONFIRMED (the blog exists and says exactly this) · INFERENCE (treating “estimated” as a hard planning date).

“Smart contract calls submitted as inner transactions of an Atomic Batch Transaction enter a six-month deprecation period, with removal planned for March 2027. Atomic batch transactions remain fully supported for composing native Hedera service operations.”Blog quote 1 — deprecation + what survives “As of September 2026: a batch may contain no more than one smart contract call, and it must be the final inner transaction.”Blog quote 2 — current constraint (matches services v0.77 behavior) “From March 2027: smart contract calls are no longer supported as inner transactions of an atomic batch.”Blog quote 3 — the removal “March 2027, estimated.”Blog, timeline — the narrowing: no committed date

Load-bearing implication. Our exact mitigation — approve + ContractCall in a batch — stops working around March 2027. No official March-2027 ban on native batches, atomic swap, or allowance behavior exists (searched; none). Stated rationale for the removal: EVM compatibility — “no equivalent construct in the EVM.” Precedent says Hedera executes such deprecations: the 2023-03-09 precompile attack (~$600K) was answered first by an emergency proxy-access shutoff and then permanently in services v0.34.5 (blocking delegatecall→precompile), followed by the HSCS Security Model v2. Plan for the sunset as real, keep the buffer, and do not let the router depend on batch inners at all.

04Why atomic batches close the race

The sweeper bot wins because a live allowance exists between two transactions. HIP-551 closes that inter-transaction gap, but atomicity alone does not guarantee zero residue when a successful contract call consumes less than approved. For redemption, restrict each batch to one iteration, reject truncation, and keep the amount at or below MIN_NET_DEBT = 1,780 HCHF; then the first trove consumes the full request or the call reverts and the approval rolls back. Larger exits are repeated chunks. CONFIRMED (contract logic and 1 HCHF mainnet result)

4.1  The one-contract-op-last rule — and why our shape fits

Mainnet constraint since 2026-09-29 (services v0.77, AtomicBatchHandler.pureChecks): a batch may contain at most ONE inner transaction that is a contract operation (CONTRACT_CALL, CONTRACT_CREATE_INSTANCE, or ETHEREUMTRANSACTION), and it must be the last inner; anything else pre-checks INVALID_TRANSACTION_BODY. Forbidden inner types (network blacklist): Freeze, AtomicBatch (no nesting), ScheduleCreate, ScheduleSign. Allowed native types include CRYPTOAPPROVEALLOWANCE and CRYPTOTRANSFER. Our mitigation shape [CryptoApproveAllowance, ContractCall] satisfies the rule exactly — confirmed in practice by the community mainnet reproduction (§3.3). Two contract calls in one batch (e.g. approve-token + redeem as two EVM calls) is not possible — approve must be the native HTS allowance transaction. CONFIRMED

Step 4 — Pre-flight: association check, price, and redemption hints

redeemCollateral needs a price and three hints. Obtain them with JSON-RPC eth_call simulations immediately before building the batch. Do not query fetchPrice() through an SDK ContractCallQuery: Hedera rejects that local query with LOCAL_CALL_MODIFICATION_EXCEPTION because the EVM path may update lastGoodPrice. JSON-RPC eth_call runs the execution-equivalent path while discarding state changes, matching the established frontend. When partialNICR is non-zero, reproduce the frontend’s getApproxHint → findInsertPosition sequence and pass the resulting upper/lower hints. The two-inner reference requires an already-associated token account (necessarily true when the account already holds HCHF). CONFIRMED

  const troveCount = Number(countResult.toString());
  let remainingTrials = Math.ceil(10 * Math.sqrt(troveCount));
  let seed = BigInt("0x" + randomBytes(32).toString("hex"));
  let bestHint = ZERO_ADDR, bestDiff;

  // Cap each getApproxHint query at 2,500 trials, retaining the closest result.
  while (remainingTrials > 0) {
    const trials = Math.min(remainingTrials, 2500);
    const approx = await hintHelpers.callStatic.getApproxHint(
      partialNICR.toString(), trials, seed.toString());
    const diff = BigInt(approx[1].toString());
    if (bestDiff === undefined || diff < bestDiff) {
      bestDiff = diff;
      bestHint = approx[0];
    }
    seed = BigInt(approx[2].toString());
    remainingTrials -= trials;
  }

  const position = await sortedTroves.callStatic.findInsertPosition(
    partialNICR.toString(), bestHint, bestHint);
  partialUpperHint = position[0];
  partialLowerHint = position[1];
}

// require amount > 0, amount <= MIN_NET_DEBT (1,780 HCHF), maxIterations = 1,
// and truncatedAmount === amount. Otherwise abort. The first trove then either
// consumes the full request or redeemCollateral reverts before the approval commits.
// Split larger exits into repeated batches.

Step 5 — Build the two inners (approve first, contract call last)

Approve exactly the requested exact-or-revert redemption chunk from step 4d. Do not proceed with a truncated amount and do not approve a large multi-trove request. batchify(client, key) sets the batch key, signs with the payer key, and freezes (forcing node account 0.0.0). The browser-wallet implementation uses the distinct ephemeral-key sequence in §6.4. CONFIRMED

6.1  Stack facts

DO NOT build on hashconnect — it is dead. Final release 3.0.14 (2025-10-02); the npm package carries the banner “shut down by 2026, upgrade to WalletConnect”; the GitHub repo is now 404. HashPack 14.3.0 (2026-06-24) removed the legacy HashConnect v2 protocol. Any hashconnect dependency is a liability and must be removed, not merely avoided. CONFIRMED
  • HashPack ≥ 14.4.0 (2026-07-17) supports batch transactions over WalletConnect — “Dapps can now bundle an associate + transfer in a single approval.” 14.4.1 added dapp-auto-approval and removed the flaky WalletConnect auto-associate that “didn’t work well with batch transactions.” This is the minimum wallet version for the batched UX — and its batch signing is now validated in practice by the community mainnet test (§3.3). CONFIRMED
  • Connector: pin @hashgraph/hedera-wallet-connect 1.5.1. That exact resolved version produced the successful test. Its DAppSigner.signTransaction returns a new signed transaction; retaining that object is load-bearing. Relay uses hedera_executeTransaction. CONFIRMED
  • SDK: keep @hashgraph/sdk 2.72.0. Approval amounts are converted to Long; each batch inner is frozen with synthetic node 0.0.0. CONFIRMED
  • What remains unverified: every protocol flow other than the exact 1 HCHF redemption, other wallets/connectors, and wallet prompt rendering. The untested single-prompt path is removed, not exposed behind a flag. UNVERIFIED

6.2  Architecture: BatchTxBuilder around the existing builders

Build raw inners first, then centralize the proven signing sequence: generate one ephemeral ED25519 batch key; set its public key and an explicit payer transaction ID on each inner; call plain freeze(); call DAppSigner.signTransaction(inner) separately and retain every returned signed transaction; assemble those returned inners; freezeWithSigner() and wallet-sign the outer; retain the returned outer; add the ephemeral private-key signature locally; relay the fully signed bytes unchanged. Never use the wallet public key as batchKey and never call freezeWithSigner() on an inner. Reference TypeScript is under code/frontend/.

6.4  Signing model — validated pattern, plus the #694 version caveat

Validated on mainnet (§3.3): exact ephemeral-key sequence, three prompts. Each inner is signed separately and replaced with the object returned by DAppSigner.signTransaction. The outer is then wallet-signed, replaced with the returned object, signed locally by the ephemeral batch key, and relayed unchanged. CONFIRMED (connector 1.5.1)
DAppSigner rebuild behavior is why returned objects are retained. Connector 1.5.1 serializes a transaction body, asks HashPack to sign it, and returns a newly decoded transaction containing that body and signature. Transaction-ID equality alone cannot prove byte equality and is not a valid issue-#694 guard. Pin the tested version and regression-test the full returned-object sequence on every upgrade.

The one-prompt hedera_signAndExecuteTransaction path is intentionally not present in the reference implementation. It has not been validated for this contract-call batch and should not be offered to users until separately proven.

6.5  UX requirements

  • Anticipate three signing prompts — and explain them before the wallet opens. The validated wallet flow (§6.4) presents one prompt per inner transaction plus one for the outer batch (inner 1, inner 2, outer). A user expecting a single prompt will suspect a bug or an attack: the UI must say three prompts are coming and show a plain-language line for each inner (approve X HCHF to wrapper 0.0.6070122; redeem X HCHF for collateral). What HashPack renders inside each prompt is UNVERIFIED — until scenario T2 lands, treat wallet rendering as unknown and make the dapp-side preview authoritative.
  • Exact-amount display, always. For closeTrove, show freshly read entire debt minus 20 HCHF. For redemption, allow only one-iteration, non-truncated chunks ≤1,780 HCHF. Never round or accept typed debt.
  • Residue allowance check + emergency revoke. Post-execution, query /accounts/{user}/allowances/tokens; residue must be 0 and the exact token debit must match. If any residue is found, surface a one-click revoke and block further operations until cleared. This check is mandatory and cannot be omitted by a caller.
  • HashPack version gate. Detect < 14.4.0 before connecting and show an upgrade path; do not silently degrade.
  • No non-atomic fallback. Unknown versions and other wallets fail closed. A warning does not make an exposed standalone approval safe.
  • Honest fee estimate. Show max fee covering the batch fee + each inner’s full fee, and state that inner fees are charged even if the batch rolls back (§4.2).

6.6  Security checklist

  • Exact-amount approvals only; no unlimited approvals anywhere in the fork (including legacy non-batched paths).
  • closeTrove approval equals freshly read entire debt minus 20 HCHF; a user-entered overestimate is unsafe.
  • batchKey is a fresh ephemeral ED25519 key generated in memory. It cannot authorize the account or inners; it signs the wallet-signed outer batch.
  • All contract/token ids from the 2026-10-05 fingerprinted set (§05 step 3) — never from repo configs; ship a verified address manifest with the frontend.
  • Canonical HLQT HTS 0.0.6070128 only — counterfeit-HLQT confusion is an active risk (§08); verify wrapper 0.0.6070127 is the spender before building.
  • Enforce the invariant in code: exactly one contract op, last position; unit-test the builder against INVALID_TRANSACTION_BODY shapes.
  • Redemption reuses the existing populated-transaction path, requires one iteration, no truncation, and a chunk ≤1,780 HCHF.
  • Log batch id + inner ids for every operation (audit + incident replay); mirror-node residue check runs before showing success.
  • Pinned dependency versions; WalletConnect project id locked to the deployer’s; supply-chain review when bumping the connector to 2.1.x.
  • The bundled registry is mainnet-only. Validate changes with the smallest practical mainnet amount and compare exact mirror-node state.

  • UNVERIFIED — how HashPack renders the inner details inside each signing prompt; wallet/connector combinations other than the validated HashPack + hedera-wallet-connect 1.5.1 path.

community-2.2 (2026-10-05). CLI redemption preflight corrected from the failed mainnet rollback test:

  • Execution-equivalent price: replaced PriceFeed.lastGoodPrice() with a read-only simulation of fetchPrice(), matching both TroveManager.redeemCollateral and the established frontend.
  • Partial insertion hints: the CLI now performs getApproxHint plus SortedTroves.findInsertPosition and passes the returned upper/lower hints. Zero/zero is retained only when the partial NICR is zero.

community-2.1 (2026-10-05). Reference code and instructions aligned to the successful mainnet transaction. One line per correction:

  • Mainnet validation — PROVEN (§3.3): a community contributor reproduced the batched redemption on mainnet — [CryptoApproveAllowance 1 HCHF] + [TroveManager.redeemCollateral] as the final inner under one parent AtomicBatch; the batch succeeded, exactly 100,000,000 units were consumed and burned, HBAR was returned, and the residue allowance was zero; the mirror record confirms ordering and shared parent. Evidence in the GitHub issue; the contributor remains unnamed unless they request attribution. Three signing prompts observed (inner 1, inner 2, outer batch).
  • closeTrove approval amount (safety-critical, §2.1/§05/§6.3/§6.6): approve exactly net debt (debt − 20 HCHF); the GasPool provides the 20 HCHF gas compensation. Approving the full debt leaves a 20 HCHF stealable allowance.
  • maxFeePercentage decimals (§05): corrected to the deployment’s 8-decimal fixed point (BaseMath DECIMAL_PRECISION = 1e8): 100% = 1e8, 0.5% floor = 500_000.
  • Redemption exactness (§05 steps 4d–5, §6.5): permit only a non-truncated request no larger than 1,780 HCHF with maxIterations = 1; otherwise abort before signing. Larger exits use repeated batches. This is the shape proven by the successful 1 HCHF mainnet test and prevents a successful call from consuming less than its allowance.
  • Router scope narrowed (§3.2/§07/§08): durable router = permissionless redemption ONLY — closeTrove/adjustTrove act on msg.sender and cannot be routed for existing users; SP exits, unstaking, and claims need no router (standalone calls keep working after March 2027); existing-user trove operations = batches until cutoff / migration / v2.
  • Signing patterns (§6.4/§6.5/§6.7): generate a one-use ED25519 batch key; freeze and wallet-sign each inner separately, retaining the returned transaction objects; assemble and wallet-sign the outer; add the ephemeral signature locally; relay the fully signed bytes with hedera_executeTransaction. Three HashPack prompts via hedera-wallet-connect 1.5.1 were validated on mainnet. Alternate and non-atomic submission paths are removed.
  • Test defaults labeled (§05): fixed gas values are test defaults; the bundled addresses are mainnet-only, so validate construction offline and then use controlled smallest-amount mainnet pilots.
